FLRA Creation Flow — Indented Steps

1. Create New FLRA Button — Step-by-Step Behavior
    1.1. Verify Authenticated Session
        - Check that the user is logged in
        - If not, show an error (e.g., "You must be logged in to create a form")
    1.2. Start Loading State
        - Visually disable the button
        - Optionally show a spinner or "Creating..." text
    1.3. Call Form Creation Service
        - Call createFormWithModules()
        - Pass the following:
            - companyId: from authenticated user
            - title: default to "New FLRA" or use passed value
            - description: optional
            - Check if user has list of modules; if not, generate stock modules for FLRA
            - moduleIds: array of module keys to scaffold (e.g., "header", "hazards", etc.)
    1.4. Handle Service Result
        - If error is returned:
            - Log error for debugging
            - Show user-friendly error message (e.g., "Form creation failed")
            - Stop loading state
            - Do not navigate
        - If formId is missing:
            - Log critical error
            - Stop loading state
            - Show "Unexpected response from server"
        - Navigate to New Form
            - Redirect user to /flra/:formId using the new form's ID
            - Optional: store returned modules and fields in global context to avoid re-fetch
        - Stop Loading State
        - Re-enable the button once creation completes or fails
    1.5. Edge Case Considerations
        - If Supabase is unreachable or throws, display a generic network error
        - If the user double-clicks the button, debounce or disable
        - If createFormWithModules returns status = 'broken', optionally show a warning prompt before redirecting
        - Confirm that user.company_id exists

2. createFormWithModules — Step-by-Step Behavior
    2.1. Validate Required Inputs
        - Ensure companyId is present
        - Ensure title is non-empty
        - Ensure moduleIds or templateLabel is provided
        - If any required input is missing, return an error immediately (error: "Missing input")
    2.2. Create a New Form Record
        - Include: company_id, optional project_id, title, description, default status = 'draft'
        - Capture the returned formId
    2.3. Loop Through Provided Modules
        - For each module key in moduleIds
            - Look up the module definition in the modules table by name
            - If the module is not found:
                - Optionally skip and log a warning
                - Or return an error (depending on implementation strictness)
    2.4. Create Form Module Record
        - For each resolved module:
            - Insert into form_modules table with:
                - form_id, module_id, module_order, and default
            - Capture the new form_module_id
    2.5. Clone Field Definitions for Each Module
        - For each new form_module:
            - Query the module_fields table (or template) for all fields belonging to that module
            - For each field:
                - Insert a row into form_module_fields with:
                    - form_id, form_module_id, name, label, type, required, default_value, etc.
            - If a field insert fails:
                - Log a warning and continue to next field
                - Do not abort the whole operation unless critical
    2.6. Fetch Field Definitions (if needed for return structure)
        - For each module:
            - Query the form_module_fields table for all fields belonging to that form_module
            - Order by field_order
    2.7. Determine Completion Status
        - If all modules + fields are inserted successfully: return status: "complete"
        - If some fields fail but modules succeed: return status: "partial" with warnings
        - If module creation fails: return status: "broken" and do not continue
    2.8. Return Result Object
        - Always return:
            - form: the newly created form (with ID)
            - modules and fields (if returnStructure = true)
            - status: "complete", "partial", or "broken"
            - error: null or an error message
    2.9. Critical Notes
        - All inserts must use Supabase .select().single() to validate responses
        - Foreign key relationships must be respected (form_id, module_id)
        - Must handle both module-based (moduleIds) and template-based (templateLabel) creation logic (if both are supported)

3. Missing or Under-Documented Steps
    3.1. Field Cloning/Copying Logic
        - After creating each form_module, you must:
            - Query module_fields for that module
            - Insert a copy of each field into form_module_fields for the new form_module
        - If you ever support template-based creation, document the lookup and cloning from module_template_fields
    3.2. Transactionality
        - If possible, wrap the entire creation process in a transaction to avoid partial/inconsistent state
    3.3. Return Structure
        - If you want to avoid re-fetching, clarify that you should return the full structure (form, modules, fields) in the result
    3.4. Error Handling Granularity
        - Document what happens if some field inserts fail (partial success, warnings, etc.)
    3.5. Concurrency/Idempotency
        - If the user double-clicks, ensure you don't create duplicate forms (debounce or check for in-progress creation)
